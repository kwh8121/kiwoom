# 개발 계획: 키움 조건검색식 조합 기반 종목 추출 웹앱

> **문서 상태:** 초안 v0.2 (검토 반영)
> **참고 자료:** [키움 저장 조건검색식 목록](../guides/kiwoom-saved-condition-searches.md), 로컬 `kiwoomcli spec` 키움 REST API 스펙(ka10171·ka10172·au10001·오류코드표)

### v0.2 주요 변경 사항

- 키움 연동 방식을 **키움 REST API의 WebSocket 조건검색(ka10171·ka10172)**으로 정리하고, 스펙으로 확인된 사실과 실제 호출로 확인할 항목을 분리했습니다(3장).
- **토큰이 발급 IP에 묶인다(오류 8010)**는 점을 반영해, Vercel은 키움을 직접 호출하지 않고 고정 IP 워커만 호출하도록 역할을 확정했습니다(4장).
- 조건식 일련번호(`seq`)가 바뀔 위험에 대비해 **실행 시점에 일련번호와 이름의 일치 여부를 검증**하도록 했습니다(5·7장).
- 표현식 AST를 타입으로 정의하고, 제외 연산의 기준 집합과 제외 집합을 구조적으로 분리했습니다(5장).
- 종목코드 접두어(`A`/`J`/`Q`) 정규화, 연속조회 완료 판정, 오류코드 분류, 실행 상태 머신, 작업 선점 방식을 구체화했습니다(6·7장).
- 실전 계좌 키를 쓰는 경우에 대비해 **워커의 호출 가능 API 허용 목록(allowlist)**을 추가했습니다(9장).
- 0단계 연동 검증에 쓸 `kiwoomcli` 명령과 기록할 항목을 명시했습니다(10장).

## 0. 한눈에 보기

- 키움에 저장된 조건식을 **다시 구현하지 않습니다.** 조건식마다 키움이 반환한 **종목 집합**에 AND·OR·EXCLUDE를 적용합니다.
- 초기 버전은 **개인 사용, 수동 실행, 국내 주식(KRX)**을 전제로 합니다. 자동 주문, 상시 실시간 감시, 백테스트는 범위에서 제외합니다.
- 구성은 `브라우저 → Next.js(Vercel) → Supabase ← 키움 워커(고정 IP) → 키움 REST API`입니다. **키움과 통신하는 구성 요소는 워커뿐입니다.**
- 첫 번째 개발 작업은 UI가 아니라 **"워커 실행 환경에서 조건식 하나의 전체 결과를 누락 없이 수집"하는 연동 검증**입니다.

## 1. 목표와 전제

### 목표

사용자가 기존 키움 조건검색식을 선택·조합해 다음을 수행할 수 있게 합니다.

1. 프로필별 저장 조건식 목록 동기화·조회
2. 조건식 조합 전략 작성·저장(버전 관리)
3. 전략 실행으로 종목 추출
4. 종목별 조건 충족 내역 확인
5. 실행 이력 조회와 직전 결과 비교
6. 결과 CSV 다운로드

### 비목표 (MVP에서 하지 않는 것)

- 주문 및 주문 관련 API 호출 전체
- 조건식 생성·수정 (조건식은 영웅문4 HTS에서만 만들고 고칠 수 있음)
- 실시간 조건검색(ka10173) 구독, 예약 실행
- 수익률 분석, 백테스트, 매수 추천

### 참고 자료의 의미와 한계

[저장 조건검색식 목록](../guides/kiwoom-saved-condition-searches.md)에는 `kiwoom-demo`·`kiwoom-real-vibe` 프로필에 각각 30개 조건식이 있고 두 프로필의 일련번호와 이름이 같다고 기록되어 있습니다. 하지만 목록 조회(ka10171) 응답에는 **일련번호와 이름만** 들어 있고, 지표 설정값·기간·내부 AND/OR 규칙은 없습니다.

- 조건식 이름을 근거로 매매 규칙을 추정해 구현하지 않습니다.
- 문서의 설명은 화면용 참고 설명으로만 쓰고, 항상 `이름 기반 추정` 표시를 붙입니다.
- 이름이 같아도 두 프로필의 조건식 내용이 같다고 간주하지 않습니다.
- 정확한 규칙은 영웅문4 `[0150] 조건검색`에서 직접 확인합니다.
- 시장 데이터 원천은 **키움으로 한정**합니다. 종목명은 조건검색 응답(필드 `302`)에 포함되므로 MVP에서는 별도 보강 소스가 필요 없습니다. KRX는 휴장일 판정이나 종목 마스터가 필요해질 때 쓰는 후속 단계 원천으로 남겨 둡니다.

## 2. MVP 범위

| 구분 | MVP 포함 | 후속 단계 |
| --- | --- | --- |
| 로그인 | Supabase Auth, 가입 차단·허용 계정만 로그인 | 다중 사용자·팀 공유 |
| 조건식 | 프로필별 목록 동기화·선택·변경 감지 | 내부 규칙 수동 메모 |
| 조합 | AND, OR, EXCLUDE, 중첩 그룹 | N개 이상 충족, 가중 점수 |
| 실행 | 버튼을 눌러 1회 조회 | 예약 실행, 실시간 감시 |
| 결과 | 종목코드·종목명·종목 유형·조건 충족 내역, 응답에 포함된 현재가·등락률 | 추가 시세·재무 정보 |
| 이력 | 실행 결과 저장, 직전 결과와 비교 | 장기 추적 |
| 내보내기 | CSV | 알림, 외부 연동 |
| 거래소 | KRX(`stex_tp=K`) | NXT·통합(`N`/`A`) |
| 주문 | 제외 (코드 차원에서 호출 차단) | 별도 프로젝트로 검토 |

**추출된 종목은 조건 조합의 결과일 뿐, 매수 추천이나 검증된 신호가 아닙니다.** 이 문구를 결과 화면에 고정 표시합니다.

### 비기능 요구

| 항목 | 기준 |
| --- | --- |
| 정확성 | 수집이 불완전하면 절대 `성공`으로 표시하지 않음 |
| 재현성 | 과거 실행은 당시 전략 버전·조건식 이름·원본 결과로 다시 설명할 수 있어야 함 |
| 실행 시간 | 리프 조건 10개, 연속조회 없음 기준 10초 이내 (0단계 추정 약 4초 = 연결 1.2초 + 0.25초 간격 × 10건) |
| 보안 | 키움 앱키·시크릿·토큰과 워커 DB 역할 비밀번호는 워커 밖으로 나가지 않음 |

## 3. 키움 연동 사실 관계

출처는 로컬 `kiwoomcli spec`(키움 REST API 스펙 사본)입니다. **"스펙 확인"은 문서상 사실이며, 실제 동작은 0단계에서 다시 확인합니다.**

| 항목 | 내용 | 상태 |
| --- | --- | --- |
| API 방식 | 키움 REST API. 조건검색은 WebSocket 사용 (Windows OCX 브리지 불필요) | 스펙 확인 |
| 엔드포인트 | 실전 `wss://api.kiwoom.com:10000/api/dostk/websocket`, 모의 `wss://mockapi.kiwoom.com:10000/...` | 스펙 확인 |
| 인증 | `au10001`(appkey·secretkey)로 접근토큰 발급 → WebSocket 연결 후 `{"trnm":"LOGIN","token":...}` 전송, 서버 `PING`은 그대로 되돌려 보냄 | 스펙·CLI 구현 확인 |
| 목록 조회 | ka10171 `trnm=CNSRLST` → `data: [[seq, name], ...]` (배열의 배열 형식) | 스펙 확인 |
| 1회 검색 | ka10172 `trnm=CNSRREQ`, `seq`, `search_type=0`, `stex_tp=K` | 스펙 확인 |
| 연속조회 | 응답 `cont_yn=Y`이면 같은 요청에 `cont_yn=Y`, `next_key`를 넣어 다시 요청 | 스펙 확인 |
| 결과 필드 | `9001` 종목코드(접두어 1자리 + 6자리, `A` 주식·`J` ELW·`Q` ETN), `302` 종목명, `10` 현재가, `12` 등락률(0 패딩, ×100 정수) 등 | 스펙 확인 |
| IP 바인딩 | 오류 8010: "Token을 발급받은 IP와 서비스를 요청한 IP가 동일하지 않습니다" | 스펙 확인 |
| 단말기 인증 | 오류 8040·8050(지정단말기)·8103 | 스펙 확인, 등록 절차는 미확인 |
| 호출 제한 | 스펙에는 1700·1701·1702가 있지만, 조건검색에서 실제로 받은 코드는 **`105110`** ("해당 TRNM으로 허용된 요청 건수를 초과"). CNSRREQ는 **약 1초에 5건**까지 허용되고, 0.25초 간격이면 제한이 없음. 같은 조건식 재조회에는 별도 제한 없음 | 0단계 확인 (주말) |
| 실전/모의 혼용 | 오류 8030·8031. 모의 미지원 API는 8104 | 스펙 확인 |
| 목록 조회 성공 | 두 프로필 모두 ka10171 `return_code=0`, `[seq, name]` 배열 30건 | 0단계 확인 |
| CNSRLST 선행 | CNSRLST 없이 CNSRREQ를 보내면 **오류 없이 무시됨**. 같은 연결에서 CNSRLST 뒤에는 정상 | 0단계 확인 |
| 추가 메시지 | 연결의 두 번째 CNSRREQ부터 `{"trnm":"CNSRREQ"}` → 데이터 응답 순서로 옴. 데이터 응답 뒤에는 추가 메시지 없음. 오류 응답에는 `seq`가 없고, 요청을 연속으로 보내면 응답 순서가 바뀔 수 있음 | 0단계 확인 |
| 0건 응답 | `return_code=0`, `cont_yn=N`, **`data: null`** | 0단계 확인 |
| 거래소 구분 | `K`·`A` 정상, `N`은 `900001` (주말 기준) | 0단계 확인 |
| 기타 오류 | `900001` 거래소 구분값 오류, `900004` 존재하지 않는 일련번호 | 0단계 확인 |
| 실전 vs 모의 | 30개 조건식 모두 종목 집합 동일 (주말 기준) | 0단계 확인 |
| 처리 시간 | 연결과 LOGIN 0.9~1.5초, CNSRLST 5~12ms, CNSRREQ 10~55ms | 0단계 확인 |

0단계 측정 결과는 [조건검색 연동 검증 결과](../references/kiwoom-condition-search-verification.md)에 정리되어 있습니다.

### 설계에 직접 반영할 결론

1. **Vercel 함수에서 키움을 호출하지 않습니다.** 토큰이 IP에 묶이고 WebSocket 세션을 유지해야 하므로, 고정 출구 IP를 가진 상시 워커가 필요합니다.
2. **검색 1회 = WebSocket 연결 1개 안에서 `LOGIN → CNSRLST → (CNSRREQ × 리프 수, 연속조회 포함)`** 순서로 처리합니다. CNSRLST를 먼저 보내지 않으면 응답이 오지 않으므로 반드시 지켜야 하며, 받은 목록은 조건식 변경 감지에도 씁니다.
3. **CNSRREQ는 한 번에 하나만 보냅니다.** 오류 응답에는 `seq`가 없어 동시에 여러 요청을 보내면 오류를 요청에 대응시킬 수 없습니다. 응답은 `trnm`과 `seq`로 대응시키고, `trnm`만 있는 메시지는 기록한 뒤 무시합니다.
4. 종목코드는 `raw_code`(예: `A005930`)와 정규화 코드(`005930`)·유형(`stock`/`elw`/`etn`)으로 나눠 저장합니다. 정규화 코드는 **영숫자 6자리**까지 허용합니다. 실제 응답에 `0010F0`, `0197X0` 같은 코드가 있었습니다.
5. `seq`는 길이 3의 문자열입니다. HTS에서 조건식을 삭제하거나 순서를 바꾸면 번호가 바뀔 수 있다고 보고, **`seq`만으로 조건식을 식별하지 않습니다**(7장 참조).

## 4. 아키텍처

### 구성 요소와 역할

| 구성 요소 | 역할 | 키움 접근 |
| --- | --- | --- |
| Next.js + TypeScript (Vercel) | 화면, 인증, 전략 저장·검증, 실행 작업 생성, 결과 조회, CSV 생성 | 없음 |
| shadcn/ui + Tailwind CSS | 조건 선택, 편집기, 테이블, 대화상자 | — |
| Supabase Auth | 로그인·사용자 식별 | — |
| Supabase PostgreSQL | 메타데이터, 전략, 작업 큐, 스냅샷, 결과. RLS 적용 | — |
| 키움 워커 (Python, 고정 IP 호스트) | 작업 선점, 키움 호출, 완전성 검사, 집합 연산, 결과 확정 | **유일한 접근 주체** |

### 데이터 흐름

```text
브라우저 ──▶ Next.js / Vercel ──▶ Supabase ◀── 키움 워커 ──▶ 키움 REST API (WebSocket)
              · 인증·소유권 검사       · runs (작업 큐)    · 아웃바운드 연결만 사용
              · 전략 검증·버전 고정    · snapshots         · 고정 IP, 앱키는 로컬에만 보관
              · run 생성(멱등 키)      · results           · 프로필(앱키)당 동시 세션 1개
```

- 워커는 **인바운드 포트를 열지 않습니다.** Supabase를 폴링(기본 2~5초)해 작업을 가져옵니다. 필요하면 나중에 Supabase Realtime 알림을 추가합니다.
- 작업 선점은 Postgres 함수 `claim_next_run(worker_id)`에서 `FOR UPDATE SKIP LOCKED`와 리스 만료 시각으로 처리합니다.
- 결과 확정은 `complete_run(...)` RPC 하나로 처리해 **스냅샷·최종 결과·상태 변경을 한 트랜잭션으로 묶습니다.**

### 권장 저장소 구조

```text
apps/web          # Next.js
apps/worker       # 키움 워커 (Python, uv): 표현식 검증·평가, 종목코드 정규화, 키움 클라이언트
packages/contracts # 표현식 검증·평가 공용 테스트 케이스(JSON)
supabase/         # migrations, RLS 정책, RPC 함수, seed(로컬 전용)
docs/
```

표현식 검증과 미리보기는 웹(TypeScript, `apps/web/src/lib/strategy/`)에서, 검증과 실제 평가는 워커(Python)에서 합니다. 두 구현이 같은 결과를 내도록 **`packages/contracts/cases/*.json`을 양쪽 테스트가 함께 사용**합니다.

워커는 Supabase service role 키 대신 전용 Postgres 역할 `kiwoom_worker`로 연결하고, `worker` 스키마의 함수만 실행할 수 있습니다. 이 함수는 PostgREST로 노출되지 않습니다.

## 5. 조건식 조합 설계

### 표현식 스키마

```ts
type StrategyExpr =
  | { type: "condition"; conditionId: string }          // 앱 내부 조건식 ID
  | { type: "and"; children: StrategyExpr[] }           // 2개 이상
  | { type: "or"; children: StrategyExpr[] }            // 2개 이상
  | { type: "exclude"; base: StrategyExpr; subtract: StrategyExpr[] }; // subtract 1개 이상

interface StrategyDefinition {
  schemaVersion: 1;
  profileId: string;
  exchange: "K";            // MVP는 KRX만
  expr: StrategyExpr;
}
```

예시: `기본종목 AND (전일고가돌파 OR 골든크로스)` (기능 설명용 예시이며 투자 전략 추천이 아님)

```json
{
  "schemaVersion": 1,
  "profileId": "profile-real-vibe",
  "exchange": "K",
  "expr": {
    "type": "and",
    "children": [
      { "type": "condition", "conditionId": "cond-basic" },
      {
        "type": "or",
        "children": [
          { "type": "condition", "conditionId": "cond-prev-high" },
          { "type": "condition", "conditionId": "cond-golden-cross" }
        ]
      }
    ]
  }
}
```

### 의미와 검증 규칙

- 사용자 입력 문자열을 파싱하거나 `eval`하지 않습니다. 편집기는 AST를 직접 만들고, 문자열은 **표시용 미리보기**로만 생성합니다.
- `exclude`는 `base − (subtract₁ ∪ subtract₂ ∪ …)`로 정의합니다. 단독 `NOT`은 전체 종목 집합(유니버스)을 정의해야 하므로 지원하지 않습니다.
- 집합 원소는 **정규화 종목코드**입니다. 같은 종목이 여러 페이지나 여러 조건에서 나와도 하나로 합칩니다.
- 검증(웹 저장 시점과 워커 실행 시점에 모두 수행):
  - 모든 `conditionId`가 전략의 `profileId`에 속하고 활성 상태일 것
  - `and`/`or`의 자식은 2개 이상, `exclude.subtract`는 1개 이상
  - 최대 깊이 5, 리프 최대 10개 (0단계 호출 제한 측정 후 조정)
  - 같은 조건식이 여러 리프에 나와도 키움 조회는 한 번만 수행
- 다른 프로필의 조건식을 섞을 수 없습니다. 이름이나 `seq`가 같아도 자동으로 대응시키지 않습니다. (후속 기능: 다른 프로필로 전략을 복제할 때 이름이 같은 조건을 **사용자가 확인한 뒤** 다시 매핑)

### 조건 충족 내역

최종 결과의 종목마다 **전략에 포함된 리프 조건식 중 어떤 조건식의 결과에 들어 있었는지**를 기록합니다(예: `기본종목 ✓ · 전일고가돌파 ✓ · 골든크로스 ✗`). 제외 조건에 걸린 종목은 최종 결과에 없지만, 진단 화면에서는 "제외됨" 목록으로 볼 수 있게 합니다.

## 6. 데이터 모델

사용자 소유 테이블에는 모두 `user_id`를 두고 RLS(`user_id = auth.uid()`)를 적용합니다. 워커는 `worker` 스키마 함수로만 쓰며, **함수가 넣는 행의 `user_id`는 대상 run에서 가져와** 다른 사용자의 데이터를 만들 수 없게 합니다.

| 테이블 | 주요 컬럼 | 제약·비고 |
| --- | --- | --- |
| `broker_profiles` | `user_id`, `alias`(워커의 앱키 별칭), `mode`(`real`/`demo`), `last_ok_at`, `last_error` | 비밀정보 컬럼 없음. 앱키와 시크릿은 워커에만 둠 |
| `conditions` | `profile_id`, `seq`, `name`, `ref_description`, `is_active`, `first_seen_at`, `last_synced_at` | unique `(profile_id, seq)` 중 활성 행만 대상(partial unique) |
| `condition_sync_events` | `profile_id`, 추가·삭제·이름 변경 내역, 시각 | 동기화 감사 기록 |
| `strategies` | `user_id`, `name`, `profile_id`, `current_version_id` | |
| `strategy_versions` | `strategy_id`, `version`, `definition`(jsonb), `condition_refs`(jsonb: id·seq·name 사본) | 생성 후 수정 금지(트리거 또는 권한으로 막음) |
| `runs` | `user_id`, `strategy_version_id`, `profile_id`, `status`, `idempotency_key`, `requested_at`, `started_at`, `finished_at`, `lease_owner`, `lease_expires_at`, `attempt`, `error_code`, `error_detail`, `window_start`, `window_end`, `market_phase` | unique `(user_id, idempotency_key)`; 프로필당 활성 실행(`queued`/`running`) 1개(partial unique) |
| `condition_snapshots` | `run_id`, `condition_id`, `seq`, `name`(사본), `started_at`, `completed_at`, `pages`, `count`, `is_complete`, `error_code` | unique `(run_id, condition_id)` |
| `condition_snapshot_members` | `snapshot_id`, `code`, `raw_code`, `instrument_type`, `name`, `price`, `change_rate` | unique `(snapshot_id, code)` |
| `run_results` | `run_id`, `code`, `name`, `matched_condition_ids`, `diff`(`new`/`kept`) | unique `(run_id, code)`; 이탈 종목은 별도 조회로 계산 |

### 실행 상태

```text
queued ──▶ running ──▶ succeeded
   │          ├──────▶ failed      (설정·인증 오류, 조건식 변경 감지, 재시도 한도 초과)
   │          └──────▶ timed_out   (전체 제한 시간 초과)
   └──▶ cancelled
running 상태에서 리스가 만료되면 → queued로 되돌림(attempt + 1), 한도를 넘으면 failed
```

- `succeeded`는 **모든 리프 스냅샷이 `is_complete = true`일 때만** 설정합니다.
- 실패한 실행의 스냅샷은 진단용으로 남기되, 비교·CSV·"최근 결과"에는 쓰지 않습니다.

## 7. 실행 흐름과 오류 처리

### 정상 흐름

1. 사용자가 전략을 실행합니다. 클라이언트는 실행 버튼을 누를 때마다 `idempotency_key`(UUID)를 만들어 보냅니다.
2. 서버가 소유권, 표현식 유효성, 프로필 활성 실행 여부를 확인하고 `runs`를 `queued`로 만듭니다. 이 시점의 전략 버전이 고정됩니다.
3. 워커가 `claim_next_run`으로 작업을 선점합니다(`running`, 리스 설정). 실행 중에는 리스를 주기적으로 연장합니다.
4. 워커가 해당 프로필의 토큰을 확보하고(캐시 → 만료 임박 시 재발급) WebSocket에 연결한 뒤 `LOGIN`을 보냅니다.
5. **`CNSRLST`로 현재 조건식 목록을 받아 변경 여부를 검증합니다.** 리프마다 `strategy_versions.condition_refs`의 `(seq, name)`이 현재 목록과 정확히 같아야 합니다. 하나라도 다르면 `CONDITION_CHANGED`로 실패 처리하고, 사용자에게 목록 동기화와 전략 확인을 안내합니다.
6. 중복을 제거한 리프 조건식마다 `CNSRREQ`를 **하나씩** 보내고(요청 간격 기본 0.25초), `cont_yn=N`이 될 때까지 같은 연결에서 연속조회를 반복합니다. `{"trnm":"CNSRREQ"}`만 있는 메시지는 건너뛰고, `seq`가 요청과 같은 데이터 응답이나 오류 응답을 기다립니다. 최대 페이지 수를 넘으면 불완전으로 판정합니다.
7. 조건식마다 시작·완료 시각, 페이지 수, 건수, 원본 종목을 스냅샷으로 저장합니다.
8. 모든 스냅샷이 완전한지 확인하고 워커의 표현식 평가기로 최종 집합을 계산합니다.
9. 직전 성공 실행과 비교해 신규·유지·이탈을 계산합니다.
10. `complete_run` RPC로 결과와 상태를 한 번에 확정합니다.

### 완료 판정

| 상황 | 판정 |
| --- | --- |
| `return_code=0`, 마지막 페이지 `cont_yn=N`, `data`가 `null` 또는 빈 배열 | **정상 0건** |
| `return_code=0`, 마지막 페이지 `cont_yn=N` | 정상 완료 |
| 연속조회 도중 연결 끊김·타임아웃 | 불완전 → 해당 조건식 전체를 처음부터 재시도 |
| `return_code≠0` | 오류 분류표에 따라 처리 |
| 응답 `seq`가 요청한 `seq`와 다름 | 불완전(프로토콜 오류) |

### 오류 분류

| 분류 | 코드 예 | 처리 |
| --- | --- | --- |
| 호출 제한 | **105110**(조건검색에서 실제 관찰), 1700, 1701, 1702 | 1초 이상 대기 후 지수 백오프로 재시도(횟수 제한). 기본 요청 간격 0.25초(설정값)를 지키면 발생하지 않아야 함 |
| 토큰 만료·무효 | 8005 (메시지에 코드가 포함된 경우 포함) | 토큰 재발급 후 1회 재시도 |
| IP·단말기 인증 | 8010, 8040, 8050, 8103 | 재시도하지 않음. 워커 호스트 IP와 키움 등록 상태 점검 안내 |
| 키·모드 설정 | 8001, 8002, 8030, 8031, 8104, 900001(거래소 구분값) | 재시도하지 않음. 프로필·전략 설정 오류로 표시 |
| 조건식 없음 | 900004(존재하지 않는 일련번호) | 재시도하지 않음. `CONDITION_CHANGED`로 처리하고 목록 동기화 안내 |
| 입력 오류 | 15xx | 재시도하지 않음. 버그로 기록 |
| 일시 오류 | 1999, 네트워크 오류, 응답 타임아웃 | 제한된 횟수만큼 재시도 |
| 응답 없음 | CNSRREQ 응답 타임아웃 | CNSRLST 선행 여부를 확인한 뒤 연결을 새로 맺어 재시도 |
| 앱 수준 | `CONDITION_CHANGED`, `INCOMPLETE_PAGINATION`, `RUN_TIMEOUT` | 실패로 확정, 원인 표시 |

사용자에게는 오류 코드와 정제한 메시지만 보여 줍니다. 토큰, 앱키, 원본 헤더는 로그에도 남기지 않습니다.

### 조회 시각 차이와 장 상태

- 조건식은 한 연결에서 순서대로 조회되므로 결과 사이에 시간 차이가 생깁니다. 결과 화면에는 **"동일 시점 교집합"이 아니라 수집 구간(`window_start`~`window_end`)**을 표시합니다.
- 수집 구간이 임계값(초기 15초. 0단계 측정 기준으로 리프 10개는 약 2.5초)을 넘으면 경고 배지를 붙입니다.
- 실행 시점의 장 구분(장전·장중·장후·주말)을 KST 시계 기준으로 기록하고, 장중이 아니면 "장 마감 이후 기준일 수 있음" 경고를 표시합니다. 휴장일 판정은 후속 단계로 둡니다.

### 동시성과 멱등성

- 같은 `idempotency_key`로 다시 요청하면 기존 run을 돌려줍니다(중복 클릭 방지).
- 프로필당 활성 실행은 1개로 제한합니다. 같은 앱키로 WebSocket 세션이 여러 개 생기지 않게 하기 위해서입니다.
- 워커 재실행·리스 만료로 같은 run이 다시 처리돼도 unique 제약과 `complete_run`의 상태 확인(`running` 상태이고 `lease_owner`가 일치할 때만 확정) 덕분에 결과가 중복되지 않습니다.

- 조건식은 동기화로만 생깁니다. 참고 자료의 30개 목록을 seed로 넣는 기능은 MVP에서 만들지 않습니다.

- 종목코드·종목명·유형·조건 충족 배지·응답 기준 현재가와 등락률

- CSV 다운로드, "투자 추천 아님" 고지

### ⑤ 실행 이력
- 전략 버전·실행 시각·프로필·상태(성공·실패·시간 초과·취소)

- 과거 결과 상세

직전 결과 비교는 기본적으로 **같은 전략·같은 프로필의 직전 성공 실행**과 합니다. 전략 버전이 다르면 비교는 하되 "버전 다름" 표시를 붙입니다.

## 9. 보안과 안전장치

- **API 허용 목록:** 워커의 키움 클라이언트는 `au10001`(토큰 발급), `au10002`(토큰 폐기), `ka10171`, `ka10172`만 호출할 수 있게 코드 차원에서 제한합니다. 주문 계열 API는 클라이언트에 구현하지 않습니다. 실전 계좌 키를 쓰는 경우 특히 중요합니다.
- **비밀정보 위치:** 키움 앱키·시크릿·토큰 캐시와 워커 DB 역할(`kiwoom_worker`) 비밀번호는 워커 호스트에만 둡니다(권한 0600 파일 또는 환경 파일). DB의 `broker_profiles`에는 별칭과 모드만 저장합니다.
- **인증:** Supabase Auth의 공개 가입을 끄고 허용된 계정만 로그인할 수 있게 합니다. 개인용이어도 RLS는 그대로 적용합니다.
- **CSV:** UTF-8 BOM을 붙입니다. `=`, `+`, `-`, `@`, 탭, CR로 시작하는 셀은 앞에 `'`를 붙여 수식 주입을 막습니다. 엑셀이 선행 0을 지울 수 있으므로 `raw_code`(예: `A005930`) 열을 함께 제공합니다.
- **로그:** 토큰·키·`authorization` 값은 마스킹합니다. 종목 결과는 로그가 아니라 DB에만 저장합니다.

`docs/references/kiwoom-condition-search-verification.md`에 다음을 기록합니다. 원본 응답은 토큰과 계좌 정보를 지운 뒤 테스트 fixture로 보관합니다.

- 페이지당 최대 건수, 결과가 많은 조건식에서 `cont_yn`·`next_key`의 실제 동작
- 연속조회가 **연결을 새로 맺어도** 이어지는지, 같은 연결 안에서만 유효한지
- 같은 조건식을 짧은 간격(예: 10초, 60초)으로 다시 조회할 때 제한 여부 (구 OpenAPI+에는 같은 조건식 재조회 제한이 있었던 것으로 알려져 있으나 REST API에도 적용되는지는 확인되지 않음)
- 조건식 여러 개를 연속으로 조회할 때 1700·1702가 발생하기 시작하는 간격
- 장중·장후·주말 응답 차이
- 모의 도메인 검색 결과가 실전과 같은 시장 데이터인지
- 워커 호스트 IP에서 토큰 발급과 검색이 되는지, 단말기·IP 등록 절차가 필요한지
- 같은 앱키로 다른 IP(로컬 PC와 워커)에서 토큰을 발급하면 기존 토큰이나 세션에 영향이 있는지
- HTS에서 조건식을 삭제하거나 순서를 바꿨을 때 `seq`가 바뀌는지(테스트용 조건식으로만 확인)

## 11. 필수 테스트

### 코어 단위 테스트
- `A = {001, 002}`, `B = {002, 003}`일 때 AND → `{002}`, OR → `{001, 002, 003}`, `A EXCLUDE B` → `{001}`
- `exclude`의 `subtract`가 여러 개일 때 합집합을 빼는지
- 빈 집합, 중복 종목, 깊은 중첩, 같은 조건식이 여러 리프에 쓰인 경우
- 스키마 위반 거부: 자식 1개인 `and`, 빈 `subtract`, 깊이·리프 수 초과, 다른 프로필 조건식
- 종목코드 정규화: `A005930` → `005930`/`stock`, `J`·`Q` 접두어, 선행 0 보존, 영숫자 코드(`A0010F0` → `0010F0`) 허용
- 등락률·가격 파싱: `000001500` → +1.50, `-00001500` → -1.50, 8자리 `00000686` → +6.86 (자릿수에 의존하지 않음)

### 워커 테스트 (fixture 기반 모의 WebSocket 서버)
- 연속조회 중간 페이지 누락·연결 끊김 시 완료 처리하지 않음
- `return_code≠0`을 정상 0건으로 처리하지 않음
- 오류 분류표대로 재시도 여부가 정해지는지(105110·1700 재시도, 8010·900004 재시도 안 함)
- `{"trnm":"CNSRREQ"}`만 있는 메시지를 무시하고, `seq`가 다른 응답이나 늦게 온 응답을 현재 요청의 결과로 쓰지 않는지
- 0건 응답의 `data: null`을 정상 0건으로 처리하는지
- 8005 발생 시 토큰을 재발급하고 1회만 재시도
- `PING`을 되돌려 보내는지, `LOGIN` 실패 처리
- `CNSRLST`의 `(seq, name)`이 바뀌었을 때 `CONDITION_CHANGED`로 실패
- 워커가 중간에 죽은 뒤 리스가 만료되면 재처리되고 결과가 중복되지 않음
- 허용 목록 밖의 API ID 호출 시 예외 발생

### 통합·보안 테스트
- 사용자 간 전략·실행·결과 접근 차단(RLS)
- 같은 멱등 키 재요청 시 run 1개만 생성, 프로필당 활성 실행 1개 제한
- 조건식 삭제·이름 변경 후에도 과거 이력 표시 유지
- CSV 수식 주입 방지, BOM, `raw_code` 열

## 13. 개발 에이전트 전달 지침

> 이 프로젝트는 키움 HTS에 저장된 조건검색식의 결과 종목 집합을 AND·OR·EXCLUDE로 조합하는 개인용 종목 추출 도구다. 조건식 이름을 해석해 지표를 다시 구현하지 마라.
>
> 키움 연동은 키움 REST API의 WebSocket 조건검색(ka10171 `CNSRLST`, ka10172 `CNSRREQ`)만 사용한다. 키움 호출은 고정 IP 워커에서만 하고, Vercel·Next.js 코드에서는 키움을 호출하지 마라. 워커 클라이언트는 `au10001`, `au10002`, `ka10171`, `ka10172`만 호출할 수 있게 허용 목록으로 제한하고, 주문 API는 구현하지 마라.
>
> 먼저 0단계 연동 검증을 수행하고 결과를 `docs/references/kiwoom-condition-search-verification.md`에 기록하라. 이 계획서 3장에서 "미확인"으로 표시된 호출 제한, 연속조회 동작, `seq` 안정성은 측정 전까지 추정해 구현하지 말고 설정값으로 분리하라. 검증 전에는 명시적으로 표시한 fixture 데이터만 사용하라.
>
> 구성은 Next.js(App Router)·TypeScript·shadcn/ui·Tailwind CSS, Supabase Auth·PostgreSQL(RLS), Vercel이다. 워커는 Python으로 작성한다. 표현식 규칙은 웹(TS)과 워커(Python)에 각각 구현하되, `packages/contracts/cases/*.json`을 양쪽 테스트가 모두 통과해야 한다. 구현 계획은 `docs/superpowers/plans/2026-10-17-kiwoom-conditions-mvp.md`를 따른다.
>
> 실행 결과는 모든 조건식 스냅샷이 완전할 때만 `succeeded`로 확정한다. 실패와 0건을 구분하고, 실행 시 `(seq, name)`이 저장된 값과 다르면 실패시켜라. 결과 확정은 RPC 한 번으로 원자적으로 처리하라.
>
> MVP는 수동 실행·전략 저장·결과 조회·이력·CSV까지다. 자동 주문·실시간 감시·백테스트는 구현하지 마라.
>
> 산출물: 소스코드, DB 마이그레이션, RLS 정책과 RPC 함수, 테스트, `.env.example`(웹·워커 분리), 배포 가이드(워커 상시 실행 포함), 연동 검증 결과 문서. 비밀정보와 원본 계좌 정보는 포함하지 마라.

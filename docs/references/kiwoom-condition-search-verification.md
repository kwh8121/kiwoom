## 3. 응답 형식

### 3.1 연결과 LOGIN

- 연결부터 LOGIN 응답까지: 2차 실행 9회 기준 0.87~1.46초(중앙값 1.17초). 1차 실행에서는 최대 2.35초
- 연결 비용이 조회 비용(10~55ms)보다 훨씬 크므로, **실행 1건에는 연결 1개를 유지**합니다.

### 3.2 CNSRLST (조건식 목록)

```json
{"trnm": "CNSRLST", "return_code": 0, "return_msg": "", "data": [["0", "급등주포착검색"], ["1", "눌림후반등자리"], "..."]}
```

- `data`는 **`[seq, name]` 배열의 배열**입니다. `seq`는 문자열입니다.
- 두 프로필 모두 30건이고, [저장 조건검색식 목록](../guides/kiwoom-saved-condition-searches.md)과 `seq`·이름이 일치합니다.
- `cont_yn`이 없어 한 번에 전부 옵니다. 응답 시간은 5~12ms입니다.

### 3.3 CNSRREQ 정상 응답

```json
{
  "trnm": "CNSRREQ", "seq": "1", "cont_yn": "N", "next_key": "", "return_code": 0,
  "data": [
    {"9001": "A0010F0", "302": "보원케미칼", "10": "000003195", "25": "2", "11": "000000205",
     "12": "00000686", "13": "0002248267", "16": "000002970", "17": "000003365", "18": "000002925"}
  ]
}
```

| 관찰 | 설계 반영 |
| --- | --- |
| `return_code`는 정수 `0`이고 `return_msg` 키는 없음 | `return_msg`가 없어도 정상 |
| **0건이면 `data: null`**, `cont_yn: "N"` (16개 조건식에서 관찰) | `null`과 `[]`를 모두 정상 0건으로 처리. `data` 키 자체가 없으면 불완전 |
| 응답 `seq`는 요청 `seq`와 일치(문자열) | 응답 대응 키로 사용 |
| `9001`은 접두어 + 6자리이며 이번에는 `A`만 관찰됨 | 접두어 분리 규칙 유지 |
| 영숫자 단축코드가 실제로 있음: `0010F0`(seq 1), `0197X0`(seq 11) | 코드 검증은 `^[0-9A-Z]{6}$` |
| `12`(등락률)는 상승 시 8자리(`00000686` = +6.86%), 하락 시 **부호 포함 8자리**(`-0000252` = -2.52%). 스펙에는 9자리로 되어 있음 | 자릿수에 의존하지 말고 부호가 있는 정수로 파싱한 뒤 ÷100 |
| 한 응답 안에서 종목 중복 없음 | 중복 제거는 방어용으로 유지 |
| 조회 응답 시간 10~55ms | — |

### 3.4 오류 응답

| 상황 | 응답 | 분류 |
| --- | --- | --- |
| 호출 제한 | `return_code=105110`, `해당 TRNM으로 허용된 요청 건수를 초과하였습니다 (TRNM=CNSRREQ)` | 재시도 가능. **스펙 오류표(1700~1702)에 없는 코드** |
| 거래소 구분 `N` | `return_code=900001`, `거래소 구분값을 확인해 주세요` | 설정 오류 |
| 없는 일련번호 `999` (1차 실행) | `return_code=900004`, `존재하지 않는 일련번호입니다.(seq=999)` | 조건식 변경 계열 |
| CNSRLST 없이 CNSRREQ | **응답 없음** | 타임아웃으로만 드러남 |

오류 응답에는 `seq`, `cont_yn`, `data`가 없고 `trnm`, `return_code`, `return_msg`만 있습니다. 앞에 bare 메시지도 오지 않습니다.

## 4. 동작 관찰

### 4.1 CNSRLST 선행 필요

| 순서 | 결과 |
| --- | --- |
| 새 연결 → LOGIN → CNSRREQ | 10초 동안 아무 메시지도 오지 않음 |
| 같은 연결에서 → CNSRLST → CNSRREQ | 정상(28건). 앞서 무시된 요청의 응답이 뒤늦게 오지도 않음 |

**CNSRLST는 연결마다 CNSRREQ보다 먼저 보내야 합니다.** 순서를 어기면 오류 없이 무시되므로, 워커는 연결 직후 항상 CNSRLST를 보내도록 고정합니다.

### 4.2 추가 메시지(bare)와 순서

2차 실행에서 수신 메시지 216개를 분류한 결과입니다(데이터 104, bare 95, 목록 9, 오류 8).

| 요청 | 수신 순서 | 관찰 횟수 |
| --- | --- | ---: |
| 연결의 첫 CNSRREQ | 데이터 | 9 |
| 두 번째 이후 CNSRREQ | `{"trnm":"CNSRREQ"}` (4~12ms) → 데이터 (10~55ms) | 93 |
| 호출 제한·거래소 오류 | 오류만 | 7 |

- 데이터 응답 뒤 0.3~1초 동안 기다렸지만 **추가 메시지는 한 번도 오지 않았습니다.**
- bare 메시지는 직전 검색이 정리되었다는 알림으로 보이지만, 공식적으로 확인된 의미는 아닙니다. 워커는 의미를 해석하지 말고 **기록만 한 뒤 무시**합니다.
- 1차 실행에서 응답을 기다리지 않고 요청을 연속으로 보냈을 때는 seq 2의 응답이 seq 4보다 늦게 왔습니다. 요청은 **한 번에 하나만** 보내야 합니다.

### 4.3 호출 제한 (V2)

요청을 하나씩 보내고 응답을 받은 뒤 다음 요청을 보내는 방식(워커와 같은 방식)으로, 간격마다 10건씩 측정했습니다.

| 요청 간격 | 10건 소요 | `105110` 발생 위치 | 회복까지 |
| --- | ---: | --- | ---: |
| 0초 | 0.09초 | 6~10번째 | 1.03초 |
| 0.1초 | 1.16초 | 6번째 | 0.52초 |
| 0.25초 | 2.70초 | 없음 | — |
| 0.5초 | 5.19초 | 없음 | — |

- 결과는 **CNSRREQ 기준 1초 구간에 5건**이라는 제한과 맞습니다. 정확한 구간 방식(고정 구간인지 이동 구간인지)은 확인하지 못했습니다.
- 같은 조건식을 0·1·5·15·30초에 다시 조회해도 제한이 없었고 결과도 같았습니다. 1차 실행에서는 65초 재조회와 새 연결 재조회도 정상이었습니다. **구 OpenAPI+의 "같은 조건식 1분 1회" 같은 제한은 관찰되지 않았습니다.**
- 권장값: **요청 간격 최소 0.25초**(약 4건/초). `105110`을 받으면 1초 이상 기다린 뒤 재시도합니다.
- CNSRLST가 같은 제한을 공유하는지는 측정하지 않았습니다.

### 4.5 거래소 구분 (V8)

| `stex_tp` | 결과 (seq 1) |
| --- | --- |
| `K` (KRX) | 28건 |
| `N` (NXT) | `900001 거래소 구분값을 확인해 주세요` |
| `A` (통합) | 28건, `K`와 동일 |

- 스펙에는 `K:KRX`만 적혀 있습니다. `N`이 원래 지원되지 않는 것인지, 주말이라 거부된 것인지는 평일에 다시 확인합니다.
- MVP는 계획대로 `K`만 사용합니다.

### 4.6 실행 시간 추정

- 리프 조건 10개 전략 기준 예상치: 연결과 LOGIN 약 1.2초 + CNSRLST 약 0.01초 + CNSRREQ 10건 × 0.25초 간격 = **약 4초**
- 연속조회가 생기면 페이지당 0.25초씩 늘어납니다(평일 측정 필요).
- 수집 구간(첫 조회~마지막 조회)은 리프 10개 기준 약 2.5초입니다.

## 6. 남은 검증

2026-10-18 구현/fixture E2E에서는 Kiwoom API를 호출하지 않았습니다. 따라서 배포 가이드 작성이나 로컬 fixture worker 동작은 V5/V6의 근거가 아니며, 아래 상태는 **미확인** 그대로입니다.

Task 15의 전체 흐름은 로컬 fixture transport를 이용해 검증했습니다. 이 검증에서는 App Key/Secret, 토큰, WebSocket, broker endpoint를 사용하지 않았습니다.

| 순서 | 항목 | 방법 |
| --- | --- | --- |
